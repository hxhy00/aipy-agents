# 质量检查与迭代

交付前逐项检查。标记“阻断”的项目未通过时，不得交付。

> **机器可检的阻断项必须用脚本，不要靠肉眼。** 交付前依次执行：
> `verify_html.py`（体积/图片/字段）→ `verify_wechat_compat.py`（渲染兼容性）→ `verify_fidelity.py`（内容保真）。
> 三个脚本退出码都为 `0`，才算通过第 1 节、第 5 节和第 2 节的大部分检查。

## 1. 内容保真（阻断）

- [ ] **`verify_fidelity.py` 退出码为 0（`fidelity_pct` = 100）**，`missing` / `extra` / `number_diff` 三项均为空。
- [ ] 除按规则排除的主标题外，正文文字逐字逐序一致。
- [ ] 数字、日期、名称、英文、标点、列表、表格和引用未改变。
- [ ] 未新增导语、总结、金句、标题、CTA、图注或互动文案。
- [ ] 导航只重复原有二级标题，正文原位置仍保留这些标题。
- [ ] 特别检查开篇导语（第一段前的引言）是否遗漏——这是历史上真实漏过的地方。

## 2. 图片同步（阻断）

- [ ] 真实图片与占位符总数等于源图片数。
- [ ] 图片或占位符顺序、上下文位置正确。
- [ ] 无无关图片替代；图片保持比例和关键信息。
- [ ] 无法提取的图片已按“此处插入原文第 X 张图片”标注并在说明中列出。

## 3. 标题与结构（阻断）

- [ ] 第一行主标题默认未在正文重复；不确定时没有误删。
- [ ] 一级、二级、三级标题层级清晰且样式不同。
- [ ] 每个含二级标题的一级标题下都有章节导航。
- [ ] 没有二级标题时未凭空生成导航。

## 4. 视觉丰富度（阻断）

- [ ] 至少使用 6 类视觉元素，并能逐项列出。
- [ ] 一级标题不是普通加粗文字；导航不是普通项目符号列表。
- [ ] 有卡片、边框、分割、纹理、重点或图片处理等明显设计。
- [ ] 每 2–4 段出现一次合理节奏变化。
- [ ] 没有连续整屏相同样式文字，也没有每段都卡片化。
- [ ] 配色、圆角、线条、阴影和图标属于同一视觉语言。

## 5. 公众号适配（阻断）

- [ ] **`verify_wechat_compat.py` 退出码为 0，`errors` 为空。** 这是最容易被忽略但代价最高的一项。
- [ ] 正文 15–16px，行高 1.75–2，间距舒适。
- [ ] 375px 宽度无横向滚动，图片自适应。
- [ ] **所有样式都是标签上的内联 `style` 属性**：无 `<style>` 标签、无 `class` 属性、无 `<script>`。
- [ ] 无伪元素（`::before`/`::after`）承载装饰，无 `:hover` 等交互态，无 `position:fixed`，无 CSS 变量，无 `@font-face`。
- [ ] 渐变仅作锦上添花；被微信过滤后，标题与卡片仍靠底色、边框、留白保持层级。
- [ ] 标签闭合，复制到预览环境后结构完整。
- [ ] **源文档的代码块全部渲染成了图片**（`scripts/code_image.py` 产物，`<img>` 引用），HTML 中无 `<pre>` 文本代码块、无 `&nbsp;`/`<br>` 手工缩进、无 `word-break:break-all`。文本代码块在微信里必然缩进丢失、长行硬折（三次真实返工）。规则见 `code_block_rules.md`。
- [ ] 代码块图片清晰（2x 渲染）、无行折断、中文注释正常显示；交付说明中列出保真核验里代码数字造成的 `number_diff` 放行项。
- [ ] 正文 ≤ 2 万字符；超限时用 `minify_inline_html.py` 无损压缩，**不得**把样式挪进 `<style>` 或删改内容。

## 6. 风格与原创性

- [ ] 风格与文章主题、读者和传播目的匹配。
- [ ] 没有默认套用固定蓝色模板。
- [ ] 学习参考时只提炼原则，未复制专有资产或标志性版式。
- [ ] 多案例融合有主次，不是拼贴。

## 7. 输出完整性

- [ ] 已提供设计分析、HTML、使用说明和自检结果。
- [ ] 已在 HTML 外提供封面与摘要建议。
- [ ] CTA、二维码和互动区只有在原文已有或用户明确要求时才进入正文。

## 8. 人工测试步骤

1. 准备含主标题、一级标题、二级标题、正文和图片的 Word 文档。
2. 上传到 AiPy 并调用本 Skill。
3. 跑 `verify_fidelity.py`，对照源文逐段检查文字、数字、名称和顺序。
4. 检查图片是否出现；无法提取时是否在原位置有明确占位。
5. 检查第一行主标题是否没有在正文重复。
6. 检查每个一级标题下是否生成对应二级标题导航。
7. 列出页面视觉元素，确认至少 6 类。
8. 检查整体风格是否匹配主题且不是固定模板。
9. 跑 `verify_wechat_compat.py`，确认样式全部内联。
10. 将 HTML 放入公众号编辑器或预览环境，检查手机宽度、行高、图片和样式兼容。
11. 将失败项记录到对应 reference，修改规则或资产后重复测试。

## 8.1 发布后必须回看草稿箱

**脚本通过 ≠ 微信接受。** `verify_html.py` 曾经放行过 `<style>` 版本，结果是预检通过、发布成功、草稿箱里只剩纯文字，用户看到才发现。所以：

- 发布后请用户到公众平台后台「草稿箱」打开预览，确认格式、图片、封面裁切都正常。
- 若发现格式丢失，先跑 `verify_wechat_compat.py` 定位是哪类写法被剥离，改完重发。
- 「发布成功」的返回值只代表 API 调用成功，不代表渲染正确。

## 8.2 已知踩坑记录（不要重复）

| 现象 | 根因 | 正确做法 |
|------|------|----------|
| 预检通过，但草稿箱里没有格式 | 样式写在 `<style>`/`class` 里，微信静默剥离 | 样式全部内联；跑 `verify_wechat_compat.py` |
| 正文超限，反复手工压缩 | 没有压缩工具，只好挤牙膏或走错路 | 跑 `minify_inline_html.py` 无损压缩 |
| 排版后发现漏了导语 | 没有反向核验，肉眼逐段检查必漏 | 跑 `verify_fidelity.py` |
| 图片报「不存在」 | HTML 与图片不在同一目录，相对路径解析不到 | 提前规划目录，图片放在 HTML 同级 `images/` 下 |
| 敏感词误报「唯一」 | 「全局唯一 ID」「唯一安全手段」是技术描述 | 人工确认后保留，但要在交付说明里写明是误报 |

## 9. 持续迭代记录

每次测试只记录可复现问题：输入类型、期望、实际、失败规则、修改文件和复测结果。优先修复阻断项，再优化视觉偏好。不要因一次案例重写整套规则。
