## 一、方案定型

### 1.1 智能体类型：**Python 工具型（conversation-tool）**

依据规范 2.2 / 4.1 / 实际案例 zoomeye-pro（Python 项目）。

**核心分工**：

| 环节 | 由谁完成 | 说明 |
|------|---------|------|
| 解析终稿（Word/MD/TXT → Markdown） | **智能体工具 `read_draft`** | 抽取标题层级、表格、内嵌图片 |
| 选模板 / 排版生成 HTML | **排版 skill `wechat-article-sop-layout`** | AI 审美判断，产出 HTML 文件 |
| 图片中转 uploadimg | **智能体工具 `publish_draft`** | 逐张上传，回填 mmbiz URL |
| 封面 add_material | **智能体工具 `publish_draft`** | 拿 thumb_media_id |
| 写入草稿箱 draft/add | **智能体工具 `publish_draft`** | 返回 media_id |
| 文字层校验（可选） | **智能体工具 `check_text`** | 标点/品牌名/敏感词 → 报告 |
| 微信渲染兼容性校验 | **skill 脚本 `verify_wechat_compat.py`** + **工具 `publish_draft` 服务端强制** | 防止草稿箱格式全丢 |
| 内容保真反向核验 | **skill 脚本 `verify_fidelity.py`** | 段落缺失/多出/错序、数字不一致 |
| 内联样式无损压缩 | **skill 脚本 `minify_inline_html.py`** | 正文超限时压缩，不引入 `<style>`/`class` |
| 代码块渲染成图片 | **skill 脚本 `code_image.py`**（Pygments + Playwright/Chromium） | 微信会折叠文本代码块空白并在字符中间硬折长行，必须转图片（v3.1 新增，三次返工教训） |

**目标链路（本期范围）**：终稿（Word/md）→ 选模板 → 排版生成 HTML → 导入后台（草稿箱）。

## 三、暴露的工具（MCP Tools）

### 3.1 `publish_draft`（核心工具）

**输入参数**：
| 参数 | 类型 | 必填 | 说明 |
|------|-----|------|------|
| html_path | string | 是 | 排版生成的 HTML 文件路径 |
| title | string | 是 | 文章标题（≤32字） |
| cover_path | string | 是 | 封面图路径（jpg/png，<2MB，建议 2.35:1） |
| digest | string | 否 | 摘要（≤120字，留空自动取正文前54字） |
| author | string | 否 | 作者名（≤16字） |

**内部流程**：
```
① 校验 title≤32 / digest≤120 / author≤16
② 读 HTML，执行微信渲染兼容性硬校验（wechat_compat.check_wechat_compat）
   → 命中 <style>/class/<script>/伪元素/position:fixed/CSS变量/@font-face 时直接拒绝发布
③ 正则抽取所有 <img src="...">（本地路径）
④ 逐张调 POST /cgi-bin/media/uploadimg → mmbiz URL
⑤ 回填 HTML 中的 src
⑥ 封面调 POST /cgi-bin/material/add_material?type=image → thumb_media_id
⑦ 体积校验：content ≤ 2万字符且 <1MB
⑧ POST /cgi-bin/draft/add → 返回 media_id
```

**为什么 ② 必须在 ③ 之前**：兼容性不合格时不应消耗图片上传配额，且必须让「发布成功」等价于「用户看到的是对的」。

**已知坑（v0.1.1 修复）**：requests 的 `json=` 参数默认 `ensure_ascii=True`，会把中文序列化成 `\uXXXX`，导致草稿箱全文显示 unicode 乱码。修复方式：在 `_post` 中手动 `json.dumps(..., ensure_ascii=False).encode("utf-8")` 后以 `data=` + `Content-Type: application/json; charset=utf-8` 发送。

**返回**：`media_id` + 成功消息（"已写入草稿箱，请在公众号后台查看"）

### 3.2 `check_text`（可选工具）

**输入**：html_path 或 text
**检查项**（来自《公众号发布全流程规范手册_v2.3》）：
- 标点规范：全角/半角混用、直引号 vs 弯引号、句末句号缺失等
- 品牌名：AiPY（大小写）
- 敏感词：接入第三方词库（调研后定）

**返回**：结构化报告（位置、原文、建议、规则依据）

## 三·补、微信渲染兼容性（v3 新增，源自一次真实事故）

### 事故经过

2026-09-14 首次真实发布：排版为了通过 2 万字符体积预检，把样式从内联 `style` 改写成 `<style>` 标签 + 短类名（`.a1`、`.nv`、`.hl`），HTML 从 20,601 字符降到 10,553，`verify_html.py` 判定通过，`draft/add` 也返回成功。但用户打开草稿箱看到的是**没有任何格式的纯文字**。

### 根因

微信草稿 API 在写入 HTML 时会**静默重写**：整体剥离 `<style>` 标签、剥离 `class` 属性，且不报错。而 `verify_html.py` 只检查「发布会不会失败」（文件、UTF-8、base64、外链、本地图片存在性、`\uXXXX`、字段长度、体积），**不检查「样式是否内联」**。于是出现「预检通过 + 发布成功 ≠ 用户看到的是对的」。

### 修复（本次实现）

| 层 | 措施 | 文件 |
|----|------|------|
| 客户端预检 | 新增 `verify_wechat_compat.py`，把「样式必须内联」作为阻断项 | `wechat-article-sop-layout/scripts/` |
| 服务端兜底 | `publish_draft` 在写草稿前强制执行同款校验，不合格直接拒绝并返回修复说明 | `wechat-sop-publish-assistant/src/wechat_compat.py` |
| 工具自检 | 新增 MCP 工具 `check_wechat_compat` | `wechat-sop-publish-assistant/main.py` |
| 流程固化 | SOP 从 5 步扩为 6 步，第 4 步变成「三个脚本顺序执行」；`quality_check.md` 第 5 节增加对应勾选项与踩坑记录表 | `SKILL.md` / `references/quality_check.md` |

### 顺带修复的两个能力缺口

1. **`minify_inline_html.py`** —— 正文超限时不再靠「挪样式到 `<style>`」这种错误解法。只做视觉等价的字符级压缩（去空格、`#ffffff`→`#fff`、`0px`→`0`、合并重复样式串），绝不引入 `<style>`/`class`。
2. **`verify_fidelity.py`** —— 同一次事故中还漏掉了文章开头的两段导语，靠临时脚本才发现。本脚本把「内容保真 100%」固化为可重复执行的阻断关卡，输出缺失/多出/错序/数字差异清单。

### 阻断判定清单（`wechat_compat`）

| 写法 | 微信行为 | 判定 |
|------|---------|------|
| `<style>` 标签 | 整体剥离 | 阻断 |
| `class` 属性 | 剥离 | 阻断 |
| `<script>` / `<link>` / `<iframe>` / `<video>` / `<canvas>` / `<form>` / `<input>` / `<button>` | 直接过滤 | 阻断 |
| `::before` / `::after` / `:hover` 等伪元素与交互态 | 不生效 | 阻断 |
| `position: fixed` / `sticky` | 降级为普通流 | 阻断 |
| CSS 变量 `var(--x)` | 不解析 | 阻断 |
| `@font-face` | 不支持 | 阻断 |
| 完全没有内联 `style` | 说明样式未内联 | 阻断 |
| `linear-gradient` | 可能被过滤 | 警告 |
| `white-space:nowrap` 无 `overflow` 兜底 | 横向溢出 | 阻断 |

## 四、微信 API 约束清单（实现必须处理）

| 约束 | 处理 |
|------|------|
| **HTML 样式必须内联** | **写入前硬校验（`wechat_compat`），不合格拒绝发布** |
| access_token 7200s 有效 | 本地文件缓存 + 提前刷新（预留 300s 余量） |
| content ≤ 2万字符 / <1MB | 写入前校验，超限报错并提示用 `minify_inline_html.py` 压缩 |
| 图片 URL 必须来自 uploadimg | 代码保证：只接受本地路径/已有 mmbiz URL |
| title≤32 / author≤16 / digest≤120 | 写入前校验 |
| thumb_media_id 必须永久素材 | 走 add_material，不用临时接口 |
| 频次限制 | token 缓存 + 请求失败退避重试 |
| 调用需服务器端/出口 IP 白名单 | AiPy 本机跑 → 用户需把本机公网 IP 加入后台白名单 |
| 账号须微信认证 | user_config 配置时提示 |

### 7.1 开发环境问题记录

**问题**：本机（公司网络）对 `files.pythonhosted.org` 做 TLS 中间拦截，证书签发者不被 uv 信任，报
`invalid peer certificate: UnknownIssuer`。`UV_NATIVE_TLS=1`、`SSL_CERT_FILE=/etc/ssl/cert.pem` 均无效。

**解决**：改用国内镜像源，已实测通过：

```bash
export UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
uv sync
```

**依赖版本锁定**：`mcp>=1.23.1,<2`。原因：官方示例代码使用 `mcp 1.x` 的 `@app.call_tool()`
装饰器写法；`mcp 2.x` 移除了 `Server.call_tool`（改为 `streamable_http_app()`），与规范示例不兼容。
按「只做成熟产品、不写兼容层」原则，直接锁定到官方示例对应的大版本。
