## 一、方案定型

### 1.1 智能体类型：**Python 工具型（conversation-tool）**

依据规范 2.2 / 4.1 / 实际案例 zoomeye-pro（Python 项目）。

**核心分工**：

| 环节 | 由谁完成 | 说明 |
|------|---------|------|
| 解析终稿（Word/MD/TXT → Markdown） | **智能体工具 `read_draft`** | 抽取标题层级、表格、内嵌图片 |
| 读排版全流程规则 | **智能体工具 `get_sop`** | 返回 SOP.md，含 14 个触发关键词与 6 步流程 |
| 查排版细则 | **智能体工具 `get_reference`** | 10 篇排版规范，按名取 |
| 取视觉素材 | **智能体工具 `get_asset`** | 5 类素材：风格示例 / 配色 / 图标 / 分割线 / 卡片片段 |
| 选模板 / 排版生成 HTML | **模型（审美判断）** | 有模板路径 → `extract_template_style`；无 → `get_reference(name="style_matrix")` |
| 图片中转 uploadimg | **智能体工具 `publish_draft`** | 逐张上传，回填 mmbiz URL |
| 封面 add_material | **智能体工具 `publish_draft`** | 拿 thumb_media_id |
| 写入草稿箱 draft/add | **智能体工具 `publish_draft`** | 返回 media_id |
| 文字层校验（可选） | **智能体工具 `check_text`** | 标点/品牌名/敏感词 → 报告 |
| 微信渲染兼容性校验 | **工具 `check_wechat_compat`（发布前自检）** + **工具 `publish_draft` 服务端强制** | 防止草稿箱格式全丢 |
| 发布可行性预检 | **智能体工具 `verify_html`** | 体积/图片/字段 |
| 内容保真反向核验 | **智能体工具 `verify_fidelity`** | 段落缺失/多出/错序、数字不一致 |
| 内联样式无损压缩 | **智能体工具 `minify_inline_html`** | 正文超限时压缩，不引入 `<style>`/`class` |
| 代码块渲染成图片 | **智能体工具 `render_code_images`** | 微信会折叠文本代码块空白并在字符中间硬折长行，必须转图片（Pygments + Pillow，不依赖浏览器） |

> 上表原为「智能体工具 + 独立 skill 脚本」混合执行，2.0.1 起全部收敛到本智能体的 13 个工具，模型不再需要在终端执行任何命令。合并过程见第九章。

**目标链路（本期范围）**：终稿（Word/md）→ 选模板 → 排版生成 HTML → 导入后台（草稿箱）。

### 1.2 不做（本期）

- ❌ 正式群发（止步草稿箱）

### 1.3 单一交付物

2.0.1 起只发一个包：**`wechat-sop-publish-assistant.dxt`**（约 125 KB / 51 个文件）。

工具层（13 个 MCP 工具）+ 知识层（`resources/` 下的 SOP、10 篇排版规范、19 个视觉素材）打在一起。用户装一个包即可跑通全流程，不再需要单独安装排版 skill 包。

## 三、暴露的工具（MCP Tools）

### 3.1 `publish_draft`（核心工具）

**输入参数**：
| 参数 | 类型 | 必填 | 说明 |
|------|-----|------|------|
| html_path | string | 是 | 排版生成的 HTML 文件路径 |
| title | string | 是 | 文章标题（≤32字） |
| cover_path | string | 是 | 封面图路径（jpg/png，<2MB，建议 2.35:1） |
| digest | string | 否 | 摘要（≤120字，留空自动取正文前54字） |
| author | string | 否 | 作者名（≤16字） |

**内部流程**：
```
① 校验 title≤32 / digest≤120 / author≤16
② 读 HTML，执行微信渲染兼容性硬校验（wechat_compat.check_wechat_compat）
   → 命中 <style>/class/<script>/伪元素/position:fixed/CSS变量/@font-face 时直接拒绝发布
③ 正则抽取所有 <img src="...">（本地路径）
④ 逐张调 POST /cgi-bin/media/uploadimg → mmbiz URL
⑤ 回填 HTML 中的 src
⑥ 封面调 POST /cgi-bin/material/add_material?type=image → thumb_media_id
⑦ 体积校验：content ≤ 2万字符且 <1MB
⑧ POST /cgi-bin/draft/add → 返回 media_id
```

**为什么 ② 必须在 ③ 之前**：兼容性不合格时不应消耗图片上传配额，且必须让「发布成功」等价于「用户看到的是对的」。

**已知坑（v0.1.1 修复）**：requests 的 `json=` 参数默认 `ensure_ascii=True`，会把中文序列化成 `\uXXXX`，导致草稿箱全文显示 unicode 乱码。修复方式：在 `_post` 中手动 `json.dumps(..., ensure_ascii=False).encode("utf-8")` 后以 `data=` + `Content-Type: application/json; charset=utf-8` 发送。

**返回**：`media_id` + 成功消息（"已写入草稿箱，请在公众号后台查看"）

### 3.2 `check_text`（可选工具）

**输入**：html_path 或 text
**检查项**（来自《公众号发布全流程规范手册_v2.3》）：
- 标点规范：全角/半角混用、直引号 vs 弯引号、句末句号缺失等
- 品牌名：AiPY（大小写）
- 敏感词：接入第三方词库（调研后定）

**返回**：结构化报告（位置、原文、建议、规则依据）

### 3.3 `check_wechat_compat`

**输入**：html_path
**作用**：服务端自检，输出 `ok/errors/warnings`，每个问题带行号定位。
**为什么要有**：让 AI 在发布前就能自查，不必等到草稿箱里才发现格式全丢。2.0.1 起与 `publish_draft` 共用同一份规则集（`src/wechat_compat.py`），不再两处维护。

### 3.4 知识层读取工具（2.0.1 新增）

| 工具 | 入参 | 返回 |
|------|------|------|
| `get_sop` | 无 | 全流程 SOP 全文（含 14 个触发关键词、6 步流程、入参与注意事项） |
| `get_reference` | `name`（10 篇排版规范名之一） | 该篇规范全文 |
| `get_asset` | `category`（5 类之一）、`name`（可选） | 素材内容；只给 `category` 时返回该类目文件清单 |

**安全边界（三者共用）**：入参只允许命中白名单文件名，不参与路径拼接；白名单用 `Path.iterdir()` 动态枚举，往包里加文件工具自动可用。路径穿越防护双层：字符串级拦截 `/ \ ..`、绝对路径、`~` 开头；读文件前再复核 `resolve()` 仍在基准目录内。单文件读取上限 512 KB，防止将来误打包进大文件打爆模型上下文。

### 3.5 预检与处理工具（2.0.1 由 skill 脚本迁移）

| 工具 | 入参 | 作用 |
|------|------|------|
| `extract_template_style` | 模板路径（HTML/截图/Markdown/案例目录） | 抽取结构化设计参数（配色、字号阶梯、间距、留白、装饰元素），供模型原创化融合 |
| `verify_html` | `html_path` + 标题/摘要/作者（可选） | 发布可行性预检：体积、图片、字段长度 |
| `verify_fidelity` | 终稿路径 + HTML 路径 + 主标题 | 内容保真 100% 反向核验：缺失/多出/错序/数字不一致 |
| `minify_inline_html` | `html_path` + 输出路径 | 内联样式无损压缩，**绝不**引入 `<style>`/`class` |
| `render_code_images` | `html_path` + 输出目录 | 围栏代码块转微信安全 PNG，回填 `<img>` |

**依赖缺失时的行为**：`render_code_images` 依赖 Pygments + Pillow，`verify_fidelity` 依赖 python-docx。缺依赖时只有对应工具返回「请重新安装本智能体」，其余工具照常可用——为此 `src/tools/` 的导入全部延迟到函数内，避免顶层导入失败连累整个 server。

## 三·补、微信渲染兼容性（v3 新增，源自一次真实事故）

### 事故经过

2026-09-14 首次真实发布：排版为了通过 2 万字符体积预检，把样式从内联 `style` 改写成 `<style>` 标签 + 短类名（`.a1`、`.nv`、`.hl`），HTML 从 20,601 字符降到 10,553，`verify_html` 判定通过，`draft/add` 也返回成功。但用户打开草稿箱看到的是**没有任何格式的纯文字**。

### 根因

微信草稿 API 在写入 HTML 时会**静默重写**：整体剥离 `<style>` 标签、剥离 `class` 属性，且不报错。而当时的体积预检 `verify_html` 只检查「发布会不会失败」（文件、UTF-8、base64、外链、本地图片存在性、`\uXXXX`、字段长度、体积），**不检查「样式是否内联」**。于是出现「预检通过 + 发布成功 ≠ 用户看到的是对的」。

### 修复（下表「2.0.1 现状」列为合并后的落点）

| 层 | 措施 | 2.0.1 现状 |
|----|------|------|
| 预检 | 把「样式必须内联」作为阻断项 | `src/wechat_compat.py`（原为独立预检脚本，2.0.1 起统一到工具层） |
| 服务端兜底 | `publish_draft` 在写草稿前强制执行同款校验，不合格直接拒绝并返回修复说明 | `src/wechat_compat.py`（与预检共用同一份规则） |
| 工具自检 | 新增 `check_wechat_compat` | `main.py` |
| 流程固化 | SOP 从 5 步扩为 6 步，第 4 步变成「三重预检顺序执行」；质量检查文档增加对应勾选项与踩坑记录表 | `resources/SOP.md` / `resources/references/quality_check.md` |

### 顺带修复的两个能力缺口

1. **`minify_inline_html`** —— 正文超限时不再靠「挪样式到 `<style>`」这种错误解法。只做视觉等价的字符级压缩（去空格、`#ffffff`→`#fff`、`0px`→`0`、合并重复样式串），绝不引入 `<style>`/`class`。
2. **`verify_fidelity`** —— 同一次事故中还漏掉了文章开头的两段导语，靠临时排查才发现。本工具把「内容保真 100%」固化为可重复执行的阻断关卡，输出缺失/多出/错序/数字差异清单。

### 阻断判定清单（`wechat_compat`）

| 写法 | 微信行为 | 判定 |
|------|---------|------|
| `<style>` 标签 | 整体剥离 | 阻断 |
| `class` 属性 | 剥离 | 阻断 |
| `<script>` / `<link>` / `<iframe>` / `<video>` / `<canvas>` / `<form>` / `<input>` / `<button>` | 直接过滤 | 阻断 |
| `::before` / `::after` / `:hover` 等伪元素与交互态 | 不生效 | 阻断 |
| `position: fixed` / `sticky` | 降级为普通流 | 阻断 |
| CSS 变量 `var(--x)` | 不解析 | 阻断 |
| `@font-face` | 不支持 | 阻断 |
| 完全没有内联 `style` | 说明样式未内联 | 阻断 |
| `linear-gradient` | 可能被过滤 | 警告 |
| `white-space:nowrap` 无 `overflow` 兜底 | 横向溢出 | 阻断 |

## 四、微信 API 约束清单（实现必须处理）

| 约束 | 处理 |
|------|------|
| **HTML 样式必须内联** | **写入前硬校验（`wechat_compat`），不合格拒绝发布** |
| access_token 7200s 有效 | 本地文件缓存 + 提前刷新（预留 300s 余量） |
| content ≤ 2万字符 / <1MB | 写入前校验，超限报错并提示用 `minify_inline_html.py` 压缩 |
| 图片 URL 必须来自 uploadimg | 代码保证：只接受本地路径/已有 mmbiz URL |
| title≤32 / author≤16 / digest≤120 | 写入前校验 |
| thumb_media_id 必须永久素材 | 走 add_material，不用临时接口 |
| 频次限制 | token 缓存 + 请求失败退避重试 |
| 调用需服务器端/出口 IP 白名单 | AiPy 本机跑 → 用户需把本机公网 IP 加入后台白名单 |
| 账号须微信认证 | user_config 配置时提示 |

### 7.3 打包器迁移记录（2026-09-23，接入 GitHub CI 时实测）

**背景**：为接入 GitHub Actions 自动打包做了实测，发现三个必须处理的问题。

**问题一：`@anthropic-ai/dxt` 已被官方废弃（只影响工具，不影响产物名）**

原 `package.json` 中的 `bun x @anthropic-ai/dxt pack` 依赖的包已停止维护并更名为
`@anthropic-ai/mcpb`。本仓库统一改用 `@anthropic-ai/mcpb@2.1.2`。

| 项 | 旧 | 新 |
|----|----|----|
| CLI 包名 | `@anthropic-ai/dxt` | `@anthropic-ai/mcpb@2.1.2` |
| 忽略规则文件 | `.dxtignore` | `.mcpbignore` |
| 产物扩展名 | `.dxt` | **`.dxt`（不变）**，理由见问题三 |
| manifest 版本字段 | `dxt_version: "0.4"` | 同左仍可用（schema 标记为 deprecated，推荐 `manifest_version`，暂不改动以免破坏宿主兼容） |

**关键行为差异（实测）**：`pack <目录>` 省略第二个参数时，产物文件名取自**目录名**、后缀沿用打包器默认值——
在 `agents/wechat-publish/` 下执行会得到 `wechat-publish.mcpb`，与目标产物名
`wechat-sop-publish-assistant.dxt` 不一致（既差目录名，也差后缀）。因此 CI 与脚本中一律显式指定输出文件名，连后缀一起显式指定。

**问题二：打包器硬校验图标必须是 PNG**

`mcpb pack` 会读取 `manifest.icon` 指向的文件并校验 PNG 魔数，SVG 直接导致打包失败：

```
ERROR: Icon validation failed:
  - Icon file must be PNG format. The file at "icon.svg" does not appear to be a valid PNG file.
ERROR: Cannot pack extension with invalid manifest
```

本项目原先两个智能体都用 `icon.svg`，均无法打包（此前用旧版 dxt CLI 可以）。

**解决**：保留 SVG 作为设计源文件，新增由它渲染的 `icon.png`（512×512，打包器推荐的显示尺寸），
`manifest.icon` 改指 `icon.png`，并在 `.mcpbignore` 中排除 `icon.svg` 以免冗余进包。

macOS 本地转换命令（无需安装额外工具）：

```bash
sips -s format png -Z 512 icon.svg --out icon.png
```

该约束已加入 `check.yml` 的「检查图标格式」步骤，避免以后新增智能体时再次踩坑。

**问题三（重要，后续补记）：产物后缀必须是 `.dxt`，不能用上游默认的 `.mcpb`**

打包器跟着改名后默认产物后缀变成了 `.mcpb`，一度直接照抄进文档与 CI。但**产物能不能被装上，取决于平台的后缀白名单，而不是 CLI 包名**——这两件事被混为一谈了：

| 层面 | 事实 |
|------|------|
| 上游 | `@anthropic-ai/dxt` → `@anthropic-ai/mcpb`，产物默认后缀随之变为 `.mcpb` |
| 平台 | AiPy Pro 2.1.0 **未跟进**：装扩展白名单 `[".zip", ".dxt"]`（`app.asar` 字符串实测），文件选择器只放行 `zip / dxt / md`，整包内 `.mcpb` 出现 0 次；AiPy 商店扩展下载链接全部以 `.dxt` 结尾；官方规范也仍写「选择 .dxt 文件导入」 |

**结论**：保留 `mcpb` CLI 作为打包器，**输出文件名显式指定为 `.dxt`**，产物 `wechat-sop-publish-assistant.dxt`。

`.dxt` 与 `.mcpb` 都是 zip 容器，改名后包内 `manifest.json` 哈希一致、内容零差异，且 manifest 里已有 AiPy 读取的 `"dxt_version": "0.1"`，所以改的只是文件名。

**踩坑记录（留档）**：**上游改名 ≠ 平台支持**。凡是「上游弃用 / 上游改名」这类结论，必须回到**目标平台的白名单实测**（这里就是 `app.asar` 里的后缀校验与文件选择器过滤器）去确认，不能直接套用上游公告。本项目已经因为直接套用公告，把产物写成 `.mcpb`，而 AiPy 装不上——同期官方规范里 `.dxt` / `python.dxt` 的写法反而是对的。判断标准很简单：**平台认的是文件后缀白名单**。

顺带澄清一个易混点：`.mcpbignore`（`mcpb pack` 读的排除规则文件）与 `.dxt`（产物后缀）名字相似但用途不同；`.dxtignore` 属旧版规则文件，`check.yml` 里对它的检查是有意保留的警告级守卫，防止有人误用后把 `.venv` 等本该排除的目录打进包。

**实测通过的完整链路**（本机 macOS arm64）：

```
fetch-ffmpeg.sh darwin-arm64  → 下载 ffmpeg 63MB + ffprobe 63MB，可正常执行
bun install --frozen-lockfile → 159 packages
bun run build                 → server.js 1.82MB
mcpb pack                     → 55.4MB 产物，9 个文件
解包后 ./vendor/darwin-arm64/ffmpeg -version → 9.0.2  ✅ 可执行位完整保留
```

## 九、2.0.0 合并记录（skill → 单一智能体）

> 本章记录的是 **2.0.0 那次合并工作本身**（对应提交 `8fd0a13`）。合并后的首个**可用**发布是 **2.0.1**：`wechat-v2.0.0` 的 Release 附件后缀为 `.mcpb`，AiPy 无法安装，请使用 `wechat-v2.0.1`。

### 9.1 背景

v3.0 交付两个 AiPy 扩展：智能体 `wechat-sop-publish-assistant.dxt` 与一个独立的排版 skill 包（zip）。用户要装两个包，且排版的关键一步——执行预检脚本——依赖模型自己在终端敲命令。

### 9.2 关键决策：为什么不能把 skill 直接塞进 .dxt

AiPy 规范里 skill 与智能体是**两种并列的项目类型**，机制不同：

| | skill | 智能体 |
|---|------|--------|
| 模型如何发现 | `SKILL.md` 的 description 关键词命中后被唤起 | 只暴露 MCP 工具 |
| 脚本如何执行 | 模型手动执行命令 | 服务端执行，模型只管调工具 |
| 分发形式 | 独立 zip，需单独安装 | `.dxt` |

把 skill 目录原样拷进 `.dxt`，文件在包里但模型**完全感知不到**，`$skill名` 引用失效——这是静默丢功能，不是合并。所以 2.0.0 做的不是「合目录」，而是**把 skill 能力翻译成工具**。

### 9.3 合并结果

**知识层** → `resources/`（31 个文件，随包分发）

| 内容 | 数量 | 读取方式 |
|------|------|---------|
| `SOP.md` 全流程规则 | 1 | `get_sop` |
| 排版规范 | 10 篇 | `get_reference(name=...)` |
| 视觉素材（风格示例/配色/图标/分割线/卡片） | 19 个 / 5 类 | `get_asset(category=..., name=...)` |

**工具层** → 13 个（原 5 + 新 8）

| 来源 | 工具 | 说明 |
|------|------|------|
| 原样保留 | `publish_draft`、`check_wechat_compat`、`check_text`、`wordlist_stats`、`read_draft` | 行为未变 |
| 脚本 → 独立工具 | `extract_template_style`、`verify_html`、`verify_fidelity`、`minify_inline_html`、`render_code_images` | 5 个 |
| 脚本 → 并入已有工具 | `read_draft`（终稿解析）、`check_wechat_compat`（兼容性） | 2 个，去重见 9.5 |
| 知识层新增 | `get_sop`、`get_reference`、`get_asset` | 3 个 |

### 9.4 破坏性变更

- **安装方式**：从装两个包变成装一个包。原 skill zip 不再发布。
- **执行方式**：模型不再需要执行任何终端命令，预检全部走工具调用。

### 9.5 顺带清理：两处孪生实现去重

| 功能 | 原两份实现 | 统一到 |
|------|-----------|--------|
| 读终稿 | skill 脚本 与 `src/parser.py`（重复约 80%） | `src/parser.py` |
| 微信兼容性校验 | skill 脚本 与 `src/wechat_compat.py` | `src/wechat_compat.py`，规则集取 skill 侧更全的那份 |

规则集取全后带来的加强：禁用标签 9 → 10 个（补 `audio`）；违规定位带行号；新增 5 类检查（`nowrap` 无配套 `overflow`、`<pre>` 文本代码块、`word-break:break-all`、重复内联样式、overflow 横向滚动）；阻断类 error 由 7 类增至 12 类。

### 9.6 新依赖

| 依赖 | 用途 | 为什么 |
|------|------|-------|
| `pygments>=2.17.0,<3` | 代码块词法分析与语法高亮 | 替代 Playwright 做高亮 |
| `Pillow>=10.3.0,<13` | `ImageFormatter` 内部画 PNG | 同上 |
| `python-docx>=1.1.2` | 终稿解析 | 原为运行时现场安装，改为正式依赖 |

**为什么代码块出图不用 Playwright**：原方案依赖 playwright + Chromium（约 150 MB），装不进 `.dxt`。保留它等于用户装完包还要额外装浏览器，正好抵消合并收益。改用 Pygments 自带的 `ImageFormatter` + Pillow，无浏览器。

**CJK 字体链**：Menlo / DejaVu Sans Mono / Courier New 都没有中文字形，会把中文注释渲染成空白。实现按平台解析中文字体候选路径（macOS 苹方/宋体、Windows 微软雅黑、Linux 思源黑体/文泉驿），逐个用 Pillow 实际加载探测；全部失效时退回 ASCII 等宽字体并明确警告「中文注释会显示为空白」，同时建议安装思源黑体。macOS 实测命中 `Songti.ttc`。

### 9.7 合并中发现并修复的三个真实 bug

1. **`verify_fidelity` 匹配 bug**：短标题（如「小节一」）会贪心吃掉正文块，导致真正文块反被误判缺失。属内容保真核验的误报，会掩盖真实缺失，必须修。
2. **`release.yml` 竞态导致每次发版误报**：脚本里 `set -o pipefail` + `grep -q` 组合，`grep -q` 命中后提前退出会让管道另一端的 `unzip` 收到 SIGPIPE（退出码 141），导致**每次发版都误报「产物缺少必需文件 main.py」**。
3. **`evals.json` JSON 结构缺陷**：第 5/6/7 条用例游离在数组外，`json.load` 直接报错。已合并回数组。

> 这三个 bug 与合并无关，是迁移过程中被顺带发现的。记在这里是因为它们都属于「长期没被跑到」的代码——合并让这些文件第一次被完整读了一遍。

### 9.8 产物与防回归

- 产物：`wechat-sop-publish-assistant.dxt`，128055 字节（约 125 KB），51 个文件（`resources/` 占 31 个）。产物后缀必须是 `.dxt`，原因见 7.3 问题三。
- `.mcpbignore` 追加 `README.md`：此前开发用 README 会被打进产物，导致 `release.yml` 不得不为它加一条「resources 外无 .md 残留」的豁免。从根因排除后该豁免可留作双保险。
- `release.yml` 追加**产物后缀闸门**：只放行 `.zip` / `.dxt`，其他后缀直接判失败。AiPy 客户端安装前会做后缀白名单校验，「打包成功」不代表「装得上」，这条闸门把平台约束固化成 CI 断言（背景见 7.3 问题三）。
- `check.yml` grep 守卫（防文档写回失效路径）：
  - `resources/` 与 `manifest.json` 禁止出现已删除的 skill 目录名或 `scripts/` 路径（`resources/evals/` 例外，允许记录历史脚本名）。
  - `src/` 与 `pyproject.toml` 禁止重新引入 `playwright`。
